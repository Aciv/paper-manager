## 重点结果

500 篇语料在 16 客户端下约 2843 req/s，混合 p95 15.9 ms；32 客户端并未明显提升吞吐，p95 增至 30.8 ms。500 篇容量本身没有出现明显退化。

500–1000 客户端时请求仍可完成，但 p95 已达数百毫秒，不能称为无感。吞吐趋平与延迟上升说明继续叠加客户端主要增加等待；未采集 API 连接池等待或详细 CPU/SQL profile，不能据此确定单一瓶颈。

## 导入

每组两批 × 20 项，保留上传并发 4、批次并发 2、下载全局并发 2、同域并发 1、同域间隔 1 秒。

| 场景 | 接收/入队 p95 ms | 下载入库完成 s | accepted | duplicate | 预期失败 |
|---|---:|---:|---:|---:|---:|
| files_unique | 737.50 | 0.91 | 40 | 0 | 0 |
| files_duplicate | 487.37 | 0.75 | 0 | 40 | 0 |
| urls_unique | 45.96 | 39.37 | 40 | 0 | 0 |
| urls_duplicate | 24.34 | 39.63 | 0 | 40 | 0 |
| urls_partial_slow | 4.76 | 39.25 | 38 | 0 | 2 |

40 个同域 URL 约 39 秒的等待，与现有 1 秒同域间隔相符。URL 入队只需几十毫秒；不能将下载等待视为数据库延迟。重复 URL 仍会下载后按内容去重，因此本轮重复 URL 同样约 39 秒，这是值得后续讨论的交互成本。

部分失败场景每批设置一个 404，共 2 个预期失败，其他 38 项成功；导入期间的 notes/PDF 背景请求全部无错误。accepted 表示源文件已入库且任务已排队，不表示所有解析/元信息流程已完成；Markdown 状态分布保存在原始 JSON 中。每组背景压力仅持续 8 秒，不覆盖长达 39 秒的完整下载等待。

## 验证与代码影响

`loadtest/` 提供隔离 make dev 编排、Go 造数/并发负载、按时间窗口汇总资源的工具；
只额外为开发脚本增加 `DEV_AUTO_RELOAD=false`，默认开发行为不变。
`.dockerignore` 排除压测目录，避免报告和夹具进入应用镜像。没有修改业务 API、数据库 schema、protobuf 或 Python 运行架构。

正式测量之后另跑一次小规模功能核验（`20261027T022455Z-62717`），不纳入性能结论：
新文件导入后源文档数由 1 增至 21，重复文件仍为 21；新 URL 后增至 41，重复 URL 仍为 41；
部分失败场景新增 19 项后为 60。行数增量与 accepted 数量一致，所有章节回读和背景请求无错误。
所有压测专用进程、容器、卷和造数文件已清理，报告保留；未触发 GitHub Action。
