# paper_manager 发行规则

状态：默认解压运行；保留可选受管理安装、手动升级、冷停检查点、恢复和受控清理。
使用步骤见 [INSTALL.md](INSTALL.md)。D3/D4 最终平台验收门槛继续保留；
当前为未签名候选包，版本号不代表已完成正式发行验收。

## 名称和版本

- 产品显示名为 `paper_manager`，初始应用版本统一为 `1.0.0`。
- `product.json` 保存发行元数据；构建时检查前端与 MCP 的应用版本一致。
  Go MCP 实现同时校验嵌入清单的版本，避免声明与实际握手版本不一致。
- 后续修复用补丁版本（例如 `1.0.1`）；新功能用次版本；不兼容变化单独评估主版本。
  应用版本与数据库迁移版本分别记录，不能据应用版本推断能否降级数据库。
- 数据库、Redis、Python、Go 和第三方包保留实际版本；schemaVersion、协议 v1、
  数据库迁移编号不改成 1.0.0。
- 产品内部 ID、现有数据目录、Go module、MCP 工具名前缀、证据链接协议和浏览器
  storage key 保持兼容；显示名称变更不触发数据搬迁。
- 新目录包和外层归档记录产品信息。旧归档缺少这些可选字段时仍可校验，不补写或
  重新标记旧的验收产物。现有 D3 内部包不能称作新生成的 1.0.0 正式发行包。
- 安装器/对外包使用产品名、应用版本和目标平台命名；内部测试通用文件名可保留。

## 默认交付：解压运行

Windows 使用 ZIP，Linux/macOS 使用 tar.gz。完整解压后直接运行根目录原生
paper_manager.exe / paper_manager，首次由管理页初始化，再启动服务。
程序保留在解压目录；用户数据保存到系统用户数据目录，不随解压目录移动。
默认入口不运行 Python 安装脚本、不复制到版本目录、不创建快捷方式。

已存在的 runtime.json 保留端口、凭据和业务数据。新入口不会因旧绝对路径而
偷偷运行旧目录组件，也不会把不同构建直接套在旧数据库上。
完整且哈希相同的副本可重新绑定；原目录缺失、构建不同或自定义路径不匹配时提示退出。
当前没有免安装模式的原地升级或向受管理安装的自动接管，不能直接覆盖旧程序冒充升级。

## 可选受管理安装：手动下载，受控切换

首版不做后台自动下载和无感替换。以下流程仅适用于通过可选安装器建立的受管理安装。
用户下载对应平台的新包，由安装器或后续
更新辅助程序配合 Launcher 完成切换；Launcher 负责服务状态和流程协调。

1. 校验目标平台、校验和、产品版本和组件兼容性，把新程序放入独立版本目录。
   下载/解压失败不触碰当前程序与用户数据。PostgreSQL 主版本升级走独立迁移流程。
2. 用户从管理页退出 Launcher，正常停止 Go、Python、Redis、PostgreSQL。
   安装器取得数据目录及程序目录锁，并检查端口和数据库冷停状态；仍在运行时拒绝更新。
3. 每次升级先生成完整持久化目录检查点；检查点失败则不执行迁移。
   [superseded] 原设计允许无数据变更时仅保留旧程序，现统一为每次升级创建检查点。
4. 切换程序目录，按已验证清单更新本应用管理的组件路径；保留端口、凭据、
   MCP 配置、论文和笔记。已有数据库不再执行 initdb。
5. 新版本通过启动、数据库和必要服务检查后才退出维护状态并标记成功。
   Windows 不能直接覆盖正在运行的 Launcher，因此文件替换由它退出后的安装器
   或独立辅助程序执行；不能让 Launcher 强行覆盖自己的可执行文件。
6. 失败时保留旧程序和检查点。没有发生数据格式变化且尚未开放写入时，可回到旧程序；
   有数据库迁移时必须按检查点恢复，不能只换旧 EXE。已经接受新写入后，恢复旧数据
   需要明确用户操作，不能自动抹掉新数据。

## 最小保护范围

暂不建设定时全量备份、云备份和复杂备份 UI，但升级检查点不能省略。
检查点清单至少记录应用/数据库版本、迁移状态、资源范围、完整性和完成状态。
数据库采用干净停止后的私有数据目录复制，或另行验证过的逻辑备份；
不复制仍在写入的 PostgreSQL 目录。Redis 持久化和任务 payload 兼容也纳入升级检查。

[superseded：实现采用下面的完整持久化目录检查点，避免恢复时缺原文件] 原设计只复制
本次受影响的资源并记录未复制 PDF 的引用。

实现复制配置、初始化标记、数据库、Redis 持久化、uploads、notes 和识别持久化产物；
缓存、日志、工作暂存和检查点自身不复制。包含 PDF/图片，避免更新后删除原件造成
旧数据库无法恢复。数据量大时复制会慢；这仍是本机升级检查点，不提供异机/磁盘故障保护。
跨 PostgreSQL 主版本不复用目录恢复方式。

## Launcher 的清理职责

清理由显式所有权清单、操作状态和活动占用决定。清单记录用途、操作 ID、版本、
最后活动时间和受保护状态。超时清理在成功安装/重试后及显式 maintenance cleanup 时执行，无需常驻清理线程。
删除失败记录并在下次重试；Windows 文件仍被使用时不强行回收。

以下是已实现的默认策略：

| 资源 | 默认保留与回收规则 |
| --- | --- |
| 未完成下载、解压暂存 | 最后活动超过 24 小时且无活动操作/占用后清理 |
| 旧程序版本 | 保留当前版本和最近两个成功旧版本；其余超过 30 天且不被恢复流程引用时清理 |
| 自动升级检查点 | 保留最近两个成功检查点；其余超过 30 天且无恢复引用时清理 |
| 最近已知可恢复检查点、失败待处理检查点 | 标记保护，不因 TTL 过期删除；成功替代或用户处理后才能解除保护 |
| 用户主动创建的备份 | 不自动过期，由用户明确删除 |
| 活动版本、正在运行的 worker 临时资源、当前数据库/论文/notes | 不能按上述 TTL 删除 |

数量与 TTL 是保守清理条件，保护标记优先，因此不是硬性磁盘上限。
多个失败检查点积累时显示占用和人工处理入口，不能为了满足配额自动删除恢复资料。
只处理本程序清单内的资源，不扫描系统临时目录或未知文件夹推测所有权。

论文、图片、notes 等业务资源的“无引用”由后端依据数据库、任务状态和文件引用判断。
Launcher 可触发维护并展示结果，不直接查一张表或凭目录名认定文件无用。
后续业务 GC 使用待回收清单、隔离期和删除前再次检查；数据库不可用、引用不明或
仍在上传/解析/导入时保留文件。这个子项独立验收，不与旧程序/下载暂存清理混在一起。

## D4 实现顺序

1. 名称、初始版本、构建元数据与发行规则。
2. 手动更新、兼容性检查、维护状态、最小升级检查点及失败恢复。
3. Launcher 管理的暂存/旧版本/检查点清理，验证保护和过期边界。
4. 平台安装器、许可审计、签名、安装升级卸载试验。

自动更新下载、定时备份、云备份和业务文件自动 GC 不混入第一版更新器。

个人开源候选包不以购买签名证书或 macOS 公证为本地使用前提；当前未签名。
随包保留第三方许可、组件版本及来源说明。项目 MIT 不替代第三方许可条件。

升级健康探针只开放 HTTP health 和 MCP 握手/探活，不运行 Asynq、catalog dispatcher、
housekeeping 或中断任务恢复。它会执行数据库迁移，因此必须先完成检查点。
公开业务入口和队列消费留到正常启动，避免验证新版本时消费已有排队任务。

快捷方式为显式可选项：默认安装不创建、不查询Windows桌面目录；--create-shortcut或
--shortcut-dir才启用。创建失败仅提示，主安装/升级验收不依赖快捷方式存在。
